# План доведення InstantDelay до повної функціональності

Цей план спирається на аудит поточної реалізації: структуру RTMP-потоку, буферизацію, relay-з'єднання, API керування, відповідність UI/IPC та наявні тести. Це план робіт, а не твердження, що всі перелічені можливості вже завершені.

## Ціль

Користувач запускає застосунок один раз, задає локальне RTMP-джерело й одну чи кілька цілей, обирає затримку, а застосунок стабільно передає синхронізовані аудіо, відео та метадані. Статус кожного сервісу й виходу зрозумілий; збої ізольовані; секрети не видаються через локальний API або діагностику.

## Поточний статус

- Проєкт має desktop UI, Rust-служби, RTMP ingest/relay, буфер і налаштовувані виходи.
- Існують Rust unit/integration тести, у тому числі синтетичний тестовий RTMP-сценарій.
- Повний сценарій із реальним енкодером, довготривалий тест і перевірка різних швидкостей/профілів ще не є релізним доказом стабільності.
- Застосунок слід позиціонувати як експериментальний, доки не пройдено критерії виходу нижче.

## Пріоритет 0 — правильність потоку та керування затримкою

### 1. Зафіксувати контракти потоку й сесій

- Формально визначити семантику URL виходу та окремого stream key: базовий URL, URL із ключем у path, кінцевий `/`, вкладені шляхи. Нормалізувати та перевіряти їх і під час збереження, і безпосередньо перед підключенням (`src/pages/Platforms.tsx`, `src-tauri/src/rtmp/relay.rs`).
- Уточнити підтримку кількох одночасних джерел. До реалізації ізольованих сесій — приймати тільки одне джерело й повертати зрозумілу відмову наступному, а не змішувати потоки в спільному буфері (`src-tauri/src/rtmp/server.rs`, `src-tauri/src/rtmp/session.rs`).
- Документувати межі: RTMP/RTMPS, кодеки, обмеження, допустиме число джерел і виходів.

**Перевірка:** unit-тести для URL/ключа та шляху; тест двох джерел підтверджує або ізоляцію, або явну відмову без змішування медіа.

### 2. Зробити старт relay декодованим і без втрат на підключенні

- Зберігати достатній початковий набір даних, поки кожен вихід не підтвердив publish; після підключення передавати metadata/codec configuration і починати відео з ключового кадру.
- Визначити повторне підключення: не надсилати стару чергу як «живий» потік, повторно синхронізуватися на metadata та наступному ключовому кадрі.
- Розділити транспорт читання/запису в relay-з'єднанні, щоб фонове читання control-повідомлень не забирало сокет у writer і не блокувало передачу медіа (`src-tauri/src/rtmp/relay.rs`).
- Всі очікування handshake/відповідей обмежити timeout; правильно обробляти peer chunk size, ping/pong, acknowledgement та закриття віддаленої сторони.

**Перевірка:** тест повільного підключення, закриття сокета, ping/control-повідомлень, повторного підключення та старту з ключового кадру; перевірити, що помилка одного виходу не зупиняє інші.

### 3. Уніфікувати семантику затримки

- Визначити таблицю переходів для Normal, Instant і Disabled та застосувати однакові правила у backend, UI, hotkeys, API та overlay (`src-tauri/src/rtmp/session.rs`, `src-tauri/src/rtmp/buffer.rs`).
- Визначити «Skip to Live»: безпечне очищення черги, перехід до актуального медіа та повторна синхронізація з ключового кадру; не залишати стару затримку активною після очищення.
- Задати поведінку зміни затримки під час ефіру: що лишається в черзі, що відкидається і як користувач бачить перехід.
- Встановити спільний бюджет пам'яті на буфер і черги виходів, з чіткою політикою переповнення й видимим індикатором.

**Перевірка:** state-transition тести для старту, зміни затримки, відключення затримки, skip-to-live, переповнення, timestamp wrap та відсутності відео.

## Пріоритет 0 — безпека та доступність сервісів

### 4. Захистити локальний API й секрети

- Застосувати auth token до кожного приватного HTTP маршруту, що змінює налаштування або повертає конфіденційні дані; CORS не вважати автентифікацією (`src-tauri/src/web/mod.rs`).
- Маскувати stream keys у відповідях API, логах, помилках і діагностичних даних; повертати окрему форму DTO без секретів.
- Залишити прив'язку сервісів до loopback за замовчуванням; відхиляти SSRF-подібні адреси на боці relay з урахуванням DNS, приватних мереж та IPv4-mapped IPv6.
- Відхиляти RTMPS, якщо TLS з перевіркою сертифікатів не реалізовано; не трактувати RTMPS як звичайний TCP.
- Додати ліміти тіла запиту, timeout, перевірки origin/CSRF для змін і тести неавторизованого доступу.

**Перевірка:** неавторизований клієнт не може читати ключі чи змінювати конфігурацію; логи та статус не містять секретів; loopback/private target політика перевірена тестами.

### 5. Зробити запуск веб-служб передбачуваним

- Незалежно запускати overlay і HTTP API відповідно до їхніх enable-перемикачів; помилка одного порту не повинна непомітно вимикати обидві служби.
- Після зміни портів/налаштувань застосовувати контрольований restart/rebind, показувати помилку та фактичний стан сервісу в UI.
- Додати readiness-стани й перевірки зайнятого порту, щоб помилка «localhost відмовив у підключенні» мала чітку причину та інструкцію відновлення (`src-tauri/src/main.rs`, `src-tauri/src/web/mod.rs`).

**Перевірка:** тест зайнятого порту, вимкнених служб, зміни порту та перезапуску; UI показує, який локальний endpoint не піднявся.

## Пріоритет 1 — узгодити інтерфейс та IPC

- Звірити кожну дію UI зі списком зареєстрованих Tauri-команд; видалити або реалізувати кнопки, що викликають відсутню команду (`src-tauri/src/main.rs`, `src-tauri/src/ipc/commands.rs`, `src/pages/`).
- Під'єднати hotkey події до того самого шару дій, що й UI; реєструвати, знімати та показувати конфлікти/помилки дозволів.
- Замість оптимістичного «успішного тесту» конфігурації виконувати реальну перевірку з timeout і точним результатом DNS/TCP/handshake/publish.
- Замінити статичні заглушки Dashboard фактичними лічильниками й станами з єдиного backend джерела істини.
- Всі мутації налаштувань мають повертати помилки збереження/застосування, а UI — показувати їх користувачу.

**Перевірка:** IPC smoke-тест для кожної видимої дії; тести на невдалий виклик, таймаут і помилку збереження.

## Пріоритет 2 — повторювані релізи

- Додати CI: frontend build/lint, Rust tests/fmt/clippy, перевірку залежностей і генерацію Windows bundle.
- Автоматизувати локальний тестовий стенд із тестовим RTMP-джерелом і локальним RTMP/HLS-приймачем; додати clock overlay для вимірювання фактичної затримки. Зовнішні програми є лише тестовими інструментами, а не runtime-залежностями InstantDelay.
- Перевірити наскрізний сценарій на Windows: запуск застосунку, джерело → ingest → затримка → вихід → перегляд, включно з повторним відкриттям застосунку та відновленням після помилок.
- Провести soak-тест на кількох бітрейтах і з кількома налаштованими виходами; зафіксувати CPU, RAM, втрати/перестановку кадрів і час відновлення.
- Публікувати лише перевірені збірки з контрольними сумами, відомими обмеженнями та чіткою позначкою експериментального/стабільного статусу.

## Порядок виконання та критерій готовності

1. Спочатку контракти URL/ключа та політика кількох джерел.
2. Потім RTMP старт/повторне підключення/ключові кадри й точна семантика затримки.
3. Далі ізоляція виходів, пам'ять, timeout і відновлення.
4. Після цього захист API та керований запуск/rebind локальних служб.
5. Узгодити UI/IPC, провести наскрізні й soak-тести, потім налаштувати релізний CI.

Реліз можна називати повноцінним лише тоді, коли всі P0 критерії виконані, реальний наскрізний тест повторюваний, секрети захищені, а збої одного сервісу/виходу не призводять до неконтрольованого припинення роботи інших.
